# 阶段三用量与审计边界

本文区分**当前可执行的单机限额**与**尚未实现的可靠计费**。虚拟 Key、模型权限和服务端 Provider Key 不依赖账单模块；不能因为账单尚未可靠就把估算值称为实际费用。

## 当前规则

| 情况 | 当前处理 | 能否作为账单依据 |
| --- | --- | --- |
| 最终响应提供输入和输出 Token | 两者相加，在响应完成时计入该用户 UTC 日/月额度 | 仅为该次响应的上游报告用量 |
| 已发送上游，但用量缺失 | 有额度的用户本周期后续请求拒绝，等待人工核对 | 不能 |
| SSE 截断或客户端在发送上游后断连 | 标记本周期用量未知，后续请求拒绝 | 不能 |
| 尚未发送上游的本地拒绝 | 不计 Token；速率窗口仅统计认证且获准选路的请求 | 不涉及 Provider 消耗 |
| 传输故障或错误响应后重试 | 每条上游尝试分别产生审计事件；未报告用量的尝试保持未知 | 启用账本后可持久核对，仍受下述崩溃窗口限制 |
| 上游提供 `venue_cost_pdollars` | 记录原值；缺失用 `-1`，不从 Token 反推价格 | 不能跨 Provider 比较 |

额度用原子计数器共享本进程多个工作线程；单个并发请求可能越过余额，多个实例之间不共享。未启用账本时重启会清零额度；启用账本后会恢复当前 UTC 日/月用量。普通 JSON 请求日志异步输出到标准错误，队列满时会丢弃并增加丢弃指标，**不是持久化审计日志**。尝试账本使用稳定租户、用户和 Provider ID，不依赖配置数组索引。

## 可靠账单的实施前提

1. 定义稳定的 `tenant_id`、`user_id`、虚拟 Key 版本、网关请求 ID、每次上游尝试 ID 和 Provider 请求 ID；审计事件只能引用这些标识，不能包含 Key、提示词或回复正文。
2. 为每次尝试保存状态与可核对的 Provider 原始用量/费用字段；上游未提供或流中断时记为 `unknown`，不能记零。对可能重复执行的重试，应保留每次尝试并支持后续 Provider 账单对账。
3. 按 Provider、模型、日期和计费项目维护版本化价目表；输入、输出、缓存、推理、工具、音频与图像不能用一个通用 Token 单价替代。没有来源或价格版本时费用保持未知。
4. 选择可持久化的单机审计存储并约定崩溃恢复：写入失败/积压时停止接纳有额度用户；重启前重放并校验事件，未对账的未知消耗继续拒绝。仅将异步标准错误日志重定向到文件不满足此要求。
5. 明确“硬额度”的时序：如果只在响应结束时结算，就必须承认单个在途请求可能超额；若要求严格预授权，应先定义最大可预留用量，并处理释放、超用及崩溃恢复。多实例之后还需要共享原子预留或中心化账务服务。

## 实施进度

`app/accounting.*` 已建立不可变、线程安全的版本化价目表与费用计算契约：按 Provider、实际服务模型和生效时间选择带来源的价格版本；输入、输出、缓存写入 TTL、推理、音频、图像、预测 Token、服务端工具、压缩及模型回退分别核算。缺价格、缺用量、非法分项和金额溢出都会得到不可结算状态，不会退化为零费用；模型回退使用旧模型自己的价格版本。

配置文件可在 `accounting.prices` 加载规则。启用非空价目表后，每个 `upstream` 必须设置唯一且稳定的 `id`，每条规则的 `provider` 必须引用其中一个 ID。规则必须包含 `provider`、`model`、`version`、`source`、生效时间区间和 `rates`；`rates.input`、`rates.output` 必填，其余计费项目按 Provider 实际规则显式填写。Token 类单价单位为皮美元/Token，工具类为皮美元/次。例如每百万 Token 3 美元应写为 `3000000` 皮美元/Token。计价结果已随逐尝试事件写入下述账本，但尚未形成完整可靠计费闭环。

网关现在通过 `RequestSink::on_attempt` 为每条上游尝试发出一次独立事件。事件以请求序号、请求墙钟起点和尝试序号标识，区分完整响应、传输故障、客户端中断、SSE 截断、被竞速胜者终止以及策略确认后主动截断，并保存 Provider 原始用量、费用、模型及请求 ID。完整错误响应触发切换时，错误腿与成功腿都会保留；字符串视图仅在回调期间有效。该回调位于事件循环热路径，接收器必须无阻塞。

配置 `accounting.ledger_path` 后，逐尝试事件进入固定容量的无锁队列，由专用线程追加为带 CRC32 的 JSON 行并对每条记录执行 `fdatasync`。每次进程启动生成 128 位实例 ID，它与请求序号、尝试序号共同形成跨重启不重复的标识。启动会校验所有完整记录，并按稳定 tenant/user ID 重放当前 UTC 日/月用量和 unknown 状态；当前月重复尝试 ID 会拒绝启动。完整坏行、符号链接、非普通文件、非当前用户所有或权限不等于 `0600` 也会拒绝启动，仅截掉崩溃留下的无换行半条尾部。队列满、追加或同步失败会永久拉低健康位，之后配置日/月额度的用户收到 503；管理指标公开账本健康状态和已持久化记录数。重试中非最终腿的已知 Token 会叠加进当前额度，已发送但用量未知的腿会把额度标为未知。启用账本时用户与租户 ID 必须使用稳定的 `[A-Za-z0-9._-]` 字符集。

```json
"accounting": {
  "ledger_path": "/var/lib/llmbridge/audit.jsonl",
  "prices": [ ... ]
}
```

当前仍不能宣称可靠账单完整闭环：队列是异步的，进程或主机在事件入队后、写盘前崩溃仍可能丢失尾部事件；只有结束事件，没有“尝试开始”意图，因此无法在重启时识别崩溃瞬间仍未结算的 Provider 调用；CRC 用于发现意外损坏，不提供防篡改认证。下一步需要增加开始/结束两阶段记录及确认协议，消除异步崩溃窗口并恢复未结算尝试。

```json
{
  "upstream": {"id": "primary", "url": "https://api.example.com"},
  "accounting": {
    "prices": [{
      "provider": "primary", "model": "model-a",
      "version": "2026-10-22", "source": "provider price page",
      "valid_from_unix_s": 1792627200, "valid_until_unix_s": 0,
      "rates": {"input": 3000000, "output": 15000000, "cached_input": 300000}
    }]
  }
}
```

**验收前不应勾选 `docs/tasks.md` 阶段三第 6 项：**还需证明写入失败、入队后崩溃和未结算尝试恢复。当前自动化已覆盖正常计价、完整坏行拒绝、半行恢复、重复尝试拒绝、重启额度重放、重试双腿、稳定身份和敏感内容不落盘，但尚未消除上述崩溃窗口。
