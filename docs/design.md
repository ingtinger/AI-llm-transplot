# AI-llm-transplot 技术设计

## 1. 项目目标

对外提供统一的 OpenAI 兼容 HTTP 接口，对内连接多个云端或本地 AI 服务。在多个用户并发访问时，网关负责身份隔离、流量控制、上游选择、协议转换、故障切换和可观测性。

## 2. 总体架构

```text
客户端
  │ OpenAI API + 用户凭证 + 会话 ID
  ▼
接入层
  │ HTTP 解析、SSE、TLS、请求边界校验
  ▼
策略层
  │ 用户认证、限流、会话粘性、负载均衡、熔断
  ▼
协议层
  │ OpenAI 与各厂商协议互转、模型名称映射
  ▼
上游连接层
  │ 连接池、超时、背压、故障切换
  ▼
OpenAI / Anthropic / Gemini / 本地推理服务
```

## 3. 会话一致性

网关默认保持无状态。客户端每次请求都应携带完整 `messages`，因此切换 AI 后不会丢失文本上下文。

客户端同时发送稳定的 `X-Conversation-Id`。安全模式的 `sticky` 路由把租户和用户标识也混入哈希，使不同用户的相同会话 ID 不共用选路起点。它只提高 Provider Prompt Cache 或本地 KV Cache 的复用概率；上游不可用时允许切换，但仍发送完整消息历史。

会话 ID 不用于保存聊天内容，也不能作为身份凭证。

## 4. 多上游路由

上游按配置文件中的数组顺序获得固定索引。每个上游包含：

- 地址和协议类型。
- 该上游使用的模型名称。
- 可选的客户端模型池 `models`；单数 `model` 是发给 Provider 的映射名称。
- 安全模式下 Provider Key 对应的环境变量名；兼容模式下可选客户端专用请求头名称。
- 运行时连续失败数和冷却截止时间。

`round_robin` 使用原子递增序号选择起点；配置模型池时，每个客户端模型有独立游标和固定上游列表。`sticky` 使用会话 ID 哈希作为池内起点。`first` 从池内首个上游开始。策略在首次选路、故障切换和冷却探测时均限定于相同模型池；无匹配模型返回 503，不回退到其他模型池。未配置任何 `upstream.models` 时保持旧行为。

## 5. 故障处理

连接拒绝、连接超时、写入失败、响应完成前 EOF 等错误，在尚未向客户端发送响应时可以切换上游。每次失败增加连续失败计数，达到阈值后打开熔断器；连续失败的冷却时间按 1、2、4、8、16 倍基础值增加，不在事件循环中等待。第三次尝试不回访本请求的起始上游。

成功响应会清空失败计数。完整的 `408`、`429` 和 `5xx` 在客户端尚未收到字节、请求原文可重建时先由 `on_reply()` 记账。内置策略默认不重放上游可能已执行的请求；只有管理员显式设置 `routing.allow_unsafe_replay=true` 时，才由 `on_status_retry()` 选择备用上游，发送后的传输故障同理。普通自定义策略保留其自身契约。总尝试次数受 `routing.max_attempts` 和数据面的固定上限共同约束。`Retry-After` 支持秒数和 IMF-fixdate，对 429/503 生效，最多采信 300 秒，期间连熔断探测也不会选中该上游。半截响应和流式上传不按状态码重试。

SSE 已经向客户端发送数据后不能透明切换，否则不同模型的两段输出会拼接成无效回答。此时只能中断流并记录失败。

启用不安全重放后，透明重试只保证客户端得到一个回答，不保证上游只执行或计费一次；聊天补全属于可能产生费用的非幂等请求。可靠计费需要跨 Provider 幂等机制及每次尝试的独立审计。

`routing.drained_upstreams` 是可热更新的上游索引列表。主线程接收 `SIGHUP` 后重新解析完整配置，只有这一字段变化且索引有效时才将 64 位摘除掩码一次性发布给共享策略；工作线程在一次选路中只读取一个掩码版本。已有请求引用的上游表、凭证与策略对象都不释放，因此可以继续完成。修改地址、模型、用户或其他字段一律拒绝并保持旧配置；新增/删除上游需要重启。这里的热加载不是整张配置表无中断替换。

## 6. 密钥隔离

安全模式由 `security.enabled` 显式开启。用户规则包含用户/租户标识、虚拟 Key 的环境变量名、模型与上游白名单、速率/并发/Token 限额、禁用状态和可选到期时间。进程启动时读取环境变量；数据面共享不可变规则，仅保留服务端密钥的非拥有视图，生命周期覆盖工作线程。`Policy::decide()` 在选路前校验唯一的 Bearer 凭证与模型权限，并将用户索引放进策略 tag 的高 32 位；重试用同一 tag 过滤授权上游。正常完成由 `RequestSink` 释放并发名额，客户端断连由 `Policy::on_abandon()` 释放。服务器只向选定 Provider 注入自己的 Key，客户端 Authorization 和 `X-Kottos-Key-*` 不作为上游凭证透传。

限流使用进程内原子计数：每分钟固定窗口与每用户同时在途请求上限，超限立即返回 429。Token 用量只读取最终 `RequestRecord` 的上游报告值，日/月周期均为 UTC；若请求已经发出而最终没有完整用量，有配置额度的用户在本周期后续请求会被拒绝。请求日志强制启用，但异步队列可能丢失记录。此机制是防止无界使用的单机控制，不是可审计的账单：重试前次尝试、单个超额在途请求和重启后的额度均不能精确结算。费用字段只记录上游提供的值，不自行换算价格。

未启用安全模式时，只有显式设置 `security.legacy_mode=true` 或 `--legacy-mode` 才保留上游兼容行为：客户端通过 `X-Kottos-Key-*` 传 Provider Key。两种模式都未选择或同时选择会拒绝启动，避免意外以无认证模式监听公网。

安全模式默认要求入口 TLS，并拒绝非回环地址的明文上游。`security.allow_insecure_http=true` 只为隔离本地 Mock 开发保留；它和兼容模式都仍绑定所有网卡，必须由防火墙或隔离网络限制访问。

## 7. 并发模型

网关使用多个共享无状态工作线程，每个线程拥有独立事件循环和连接池，通过 `SO_REUSEPORT` 共同监听端口。路由策略由所有工作线程共享，因此健康状态使用原子变量维护，不在热路径持有互斥锁。

## 8. 演进方向

阶段二在数据端口之外增加独立的 `127.0.0.1` 管理监听，默认关闭。`/health` 仅表示管理线程可应答；`/ready` 读取进程内路由冷却及 `Retry-After` 限制状态，并不探测 Provider 的真实可达性。Prometheus 指标只使用固定上游索引，不把用户、会话或密钥作为标签。请求完成信息经 `RequestSink` 更新原子计数；可选 JSON 请求日志先进入有界队列，由专用线程输出，满队列时丢弃并计数，不阻塞事件循环。

当前只支持单机进程内限额；尚无真实多实例需求，因此不在阶段四引入 Redis。未来若需要共享计数，认证请求在 Redis 不可用时默认拒绝，避免无限额调用 Provider；只保存计数和必要路由元数据，不保存请求体或聊天历史。聊天上下文仍由客户端每轮携带，不能让 Redis 路由状态替代对话历史。
